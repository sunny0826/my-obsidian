# 你的 AI 不是"蠢"——它只是需要一个更好的 Harness

> **原文**：[Your AI Isn't "Stupid" — It Just Needs a Better Harness | Lychee Technology Engineering Blog](https://blog.ltbase.dev/posts/agents/harness-engineering)  
> **翻译日期**：2026-04-18

**TL;DR.** Agent 失败不是因为模型弱，而是因为系统没有定义。

一个好的 harness 做四件事：
- 约束模型能做什么
- 将必须记住的内容外化
- 验证它采取的每一步
- 出错时能够恢复

## 问题：第 10 步崩溃

想象你部署了一个自主 Agent 来撰写市场研究报告。第 1-3 步执行得很完美：它规划任务、搜索网页、提取竞品数据。

但到了第 7 步，它开始凭空编造统计数据——因为搜索工具的载荷超过了上下文窗口，被静默截断了。到了第 10 步，它输出了一串损坏的 JSON，因为环路上没有 schema 验证器。整个 pipeline 崩溃了。

我们都见过这种"Agent 崩溃"。在那一刻，很容易把责任推给模型的推理能力。但在生产级 AI 中，问题通常不在于马，而在于缰绳。

## 根本原因：AI 工程范式的转变

过去两年，整个行业一直把 AI 失败当作沟通问题。如果模型失败了，我们就假设只需要更好地提问或喂给它更好的文档。但对于长周期、自主执行的任务，这些方法会遇到硬天花板。

我们现在正在进入 **Harness Engineering** 的时代——这是一门围绕模型设计系统的学科。Agent 不仅仅是 LLM，它是嵌入在严格的代码脚手架、状态管理和恢复工作流中的 LLM。

以下是领域是如何演进的：

| 时代 | 重点 | 局限性 |
|------|------|--------|
| Prompt Engineering | 指令：如何提问 | 脆弱；各步骤之间零持久性 |
| Context Engineering | 信息：需要知道什么（如 RAG） | 无状态；无法控制长周期执行 |
| Harness Engineering | 系统设计：如何约束和运行 | 解决连续的、多步骤执行控制 |

每个时代并非取代前一个时代——而是包含了它。好的 Harness 工程仍然需要好的 prompt 和好的上下文。但它增加了前两者都无法提供的执行层。

自然的下一步问题是：**这个执行层实际上是什么样的？**

不是概念上的——而是结构上的。如果模型不再是系统本身，那它坐在哪里？什么环绕着它？什么控制着它？

在高层次上，一个生产级 Agent 系统是这样的：

```
┌─────────────────────────────────┐
│          User Request           │
└────────────────┬────────────────┘
                 ▼
┌─────────────────────────────────┐
│       HARNESS (7 layer stack)   │
│  ┌───────────────────────────┐  │
│  │     LLM (The Model)       │  │
│  └───────────────────────────┘  │
└────────────────┬────────────────┘
                 ▼
┌─────────────────────────────────┐
│        Verified Output          │
└─────────────────────────────────┘
```

模型**在** harness **里面**。它从不直接对用户说话，也从不接受监督就与外部世界通信。每个输入在进入时都被过滤；每个输出在出去时都被验证。

## 好 Harness 的设计原则

在我们深入具体的层之前，值得建立一些指导每个设计决策的原则。当你不确定你的 harness 是否在发挥作用时，回到这四个测试：

**1. 约束，而不是指令。**
如果可以用程序化方式限制选择，就永远不要依赖模型"正确选择"。一个说"始终以有效 JSON 响应"的 prompt 是一个希望。一个拒绝格式错误输出的 schema 验证器是一个保证。

**2. 外化状态。**
如果一条信息对任务的连续性重要——已经做了什么、什么在等待、什么失败了——它必须存在于上下文窗口之外。上下文窗口是易失的。磁盘上的文件不是。

**3. 让每一步可验证。**
如果你无法检查它，你就无法信任它。Harness 的每一层都应该产生能够被生成它的模型以外的东西验证的输出。

**4. 本地失败，而不是全局失败。**
单个工具调用失败应该触发该步骤的重试——而不是整个 pipeline 的重启。任何失败的爆炸半径都应该尽可能小，让你的状态管理允许。

这些不是抽象的理想。它们是具有直接实现后果的工程约束，你会在下面的堆栈中看到它们中的每一个反复出现。

## 7 层 Harness 堆栈

一个健壮的 harness 不仅仅是来回传递文本。它编排一个类型化的、有状态的、可观测的系统。以下是生产级堆栈在底层的实际样子。

### 1. 认知（Cognition）

基础层。它限制模型的运行边界。Harness 不是喂给模型一个庞大的、百科全书式的系统 prompt，而是提供一张本地化的"地图"：当前角色、成功标准，以及严格的负面约束——不要做什么。把它想象成给模型一份工作描述，而不是一本百科全书。

在实践中，这通常采用结构化 system prompt、角色文件（如 agents.md）或动态生成的、针对单步的任务简报的形式。

### 2. 工具（Tools）

Harness 不是简单地将原始工具输出传回 LLM。它充当严格的中间件层，应用：

- **排序**：使用嵌入相似度或 BM25 评分来仅呈现最相关的结果。
- **去重**：在浪费宝贵 token 之前剥离重复数据。
- **Token 预算截断**：对工具载荷设置硬上限以防止上下文溢出——正是我们开篇示例中的确切失败模式。

### 3. 契约与接口（Contracts & Interfaces）

这是大多数团队跳过的层——也是造成最多神秘生产故障的层。

模型说的是概率。Harness 必须说类型。

系统中的每个边界——LLM 和工具之间、一个 Agent 和另一个 Agent 之间、harness 和外部世界之间——都需要一个明确的契约：严格的 JSON schema、类型化函数签名、版本化 API 规范。没有这个，就会出现 schema 漂移：模型一次把 price 字段生成字符串，下一次生成浮点数，你的下游 pipeline 静默地产生垃圾。

契约层在每个边界跨越处验证输入和输出，拒绝任何不符合规范的内容，防止它传播。这是原则 1（约束，而不是指令）发挥作用的地方。没有契约，微妙的 schema 漂移可能静默破坏下游系统，例如价格字段从浮点数切换到字符串而不会破坏 pipeline，但会破坏分析。

### 4. 编排（Orchestration）

没有这层，LLM 往往会无限循环、跳过关键步骤或过早宣布胜利。Harness 强制执行结构化工作流——有向无环图（DAG）或状态机——定义合法转换：Plan → Gather → Draft → Verify。模型提议动作；harness 决定允许哪些动作。

### 5. 记忆与状态（Memory & State）

状态必须被显式管理以防止遗忘。一个成熟的 harness 将记忆分成两层：

- **工作记忆（短期）**：当前步骤所需的即时对话和上下文窗口。
- **持久状态（长期）**：一个结构化文件（如 state.json），追踪哪些子任务是待处理、进行中还是已完成——跨上下文重置甚至跨会话存活。

这是原则 2（外化状态）的实践。如果一条信息只存在于上下文窗口内，它最终会丢失。

### 6. 评估与观测（Evaluation & Observation）

系统不能仅依赖"另一个 LLM prompt"来验证。评估层必须是异构的：

- **基于规则的检查**：验证 JSON schema、字符串长度或必填字段。
- **基于工具的验证**：通过编译器运行代码、执行测试套件，或使用浏览器自动化（如 Playwright）在物理上测试 UI。
- **LLM 即裁判**：仅用于主观或语义评分——语调、连贯性、用户友好性——确定性检查无法适用的地方。

### 7. 约束与恢复（Constraints & Recovery）

在自主环境中，工具失败和 API 超时是常态，不是异常。Harness 必须强制幂等性：如果一步失败，系统重试那个特定步骤而不破坏整体状态或重复先前的工作。这正是将脆弱的演示变成弹性系统的原因——这是原则 4（本地失败，而不是全局失败）的具体体现。

## 示例：一次完整的 Agent 运行

为了看看这些层如何防止崩溃，让我们追踪我们的市场研究 Agent 的完整周期——包括一个真实的失败。

**Step 1 — 用户请求**："比较竞品 A 和竞品 B 的定价。"

**Step 2 — 编排与状态**：Planner LLM 将其分解为带有两个并行分支的 DAG。state.json 将"获取竞品 A"标记为 `IN_PROGRESS`。

**Step 3 — 工具调用**：LLM 触发网络搜索。工具层获取 50 个结果，应用 BM25 排序，去重重叠文本，仅返回前 3000 个 token——在预算范围内。契约层在将输出传递给模型之前根据预期 schema 验证工具输出。

**Step 4 — 评估**：LLM 生成定价数据。评估层运行基于规则的 schema 检查，发现 JSON 缺少必填的 currency 字段。

**Step 5 — 恢复**：Harness 在用户看到错误之前拦截了错误。因为动作是幂等的，它将确切的错误追踪传回 LLM 进行本地重试——无需重启整个 pipeline。

**Step 6 — 状态更新**：修正后的数据通过验证。state.json 将竞品 A 标记为 `COMPLETED`，harness 移动到竞品 B。

**Step 7 — 硬失败**：竞品 B 的网络搜索工具返回空结果——网站宕机了。Harness 检测到空载荷，记录失败，并触发 fallback：使用替代搜索查询重试。关键的是，state.json 此时保持不变——在步骤完全成功之前不会写入部分或损坏的数据。

**Step 8 — Fallback 成功**：替代查询返回有效结果。契约层验证 schema，评估层确认所有必填字段都存在，直到此时 state.json 才将竞品 B 标记为 `COMPLETED`。

这个循环在长时间运行的任务中会重复数十或数百次。与我们介绍中的第 10 步崩溃不同，当工具完全失败时，系统吸收了冲击并在没有人工干预的情况下恢复。没有幻觉。没有静默失败。没有崩溃。

## 高级陷阱：前线的 4 个教训

当你将此架构扩展到运行数小时后，会出现新的失败模式，再多的 prompt 调优也无法修复。以下是四个在生产中 consistently 让团队栽跟头的。

### 陷阱 1："上下文焦虑"现象

随着 Agent 工作和上下文窗口填满，模型往往表现出一种行为转变，从业者们称之为"上下文焦虑"。当接近 token 限制——通常超过 70% 容量——或延迟飙升时，模型开始跳过步骤或过早完成任务。它表现得匆忙，就好像能感觉到墙壁在逼近。

**修复**：就地摘要不够——它仍然让模型在杂乱的、退化的上下文中操作。相反，执行上下文重置。Harness 监控利用率并以编程方式触发重置：

```python
# 这个阈值是经验性的，应该根据模型和工作负载进行调整。
if (tokens_used / max_context) > 0.7:
    save_state_to_disk(state)
    terminate_current_instance()
    launch_fresh_agent(state)
```

Harness 将确切的项目状态保存到持久存储，终止当前 LLM 实例，并启动一个具有干净上下文窗口的全新 Agent。新 Agent 读取保存的状态，定位自己，然后继续。这很昂贵，但对于超过单个上下文窗口的任务来说明显更可靠。

### 陷阱 2：自我评分幻觉

如果你让 AI 给自己的作品打分，它往往会以不应有的自信批准平庸的输出。这不是任何特定模型的 bug——这是一个结构性缺陷。生成输出的权重在批判它方面处于不利地位。

**修复**：使用 Sprint Contract 实现严格的关注点分离。工作开始前，Generator Agent 和独立的 Evaluator Agent 协商一个具体的、可测试的"完成"定义。两条规则是不可妥协的：

首先，Evaluator 必须执行：它应该运行代码，在无头浏览器中验证接口，或根据 schema 检查输出——而不只是读取原始文本然后做出判断。无法伪造的验证是唯一算数的验证。

其次，Evaluator 必须在干净的上下文中操作，而不是 Generator 的完整推理轨迹。如果 Evaluator 读取 Generator 的思维链，它就继承了 Generator 的假设和盲点——违背了独立评审的整个目的。给 Evaluator 输出和成功标准。仅此而已。

### 陷阱 3：优化正确性的幻觉

当 LLM 受到不可能或相互矛盾的约束时——修复这个 bug，但不要改变任何代码；让它更短，但要包含所有内容——从业者观察到一种一致的行为模式。模型停止尝试解决实际问题，转而优化看起来正确。输出变得流利但空洞：幻觉数据、表面合理但 broken logic，或在技术上满足 prompt 字面意思同时违反其意图的答案。

关于 steering vectors 和内部模型表示的最新研究——包括 Anthropic 在探测语言模型内部状态方面的工作——表明这不仅仅是表面层面的文本预测出错。在相互矛盾的压力下，模型的内部状态似乎出现了可测量的转变，尽管这一研究方向仍处于早期阶段。

**修复**：实际的要点很简单。LLM 根据当前上下文的轨迹预测下一个 token。如果你的 harness 反馈的是激进的、情绪化的错误信息（"你太蠢了，这完全错了"），你就将上下文偏向失败叙事——模型的后续输出往往会进一步退化。Harness 反馈必须保持严格客观：提供编译器错误、失败的断言、schema 不匹配。给模型一个要解决的问题，而不是一个要背负的名声。

### 陷阱 4：记忆整合周期

对于 Agent 作为长期运行的系统，持久状态管理不是一次性设置。随着时间推移，记忆日志变得臃肿和矛盾——旧决策与新决策冲突，冗余条目在每次读取时浪费 token。

一些生产 Agent 系统采用了通常称为 Memory Consolidation 的方法：一种自动化例程，定期处理和压缩 Agent 积累的工作日志。使用此模式的团队报告（参考开源 Agent 框架和 Anthropic 自身工具中的引用）显示了令人印象深刻的结果——在一个有文档记录的实例中，一个 harness 将 32K token 的嘈杂、重复历史压缩成干净的 7K token 状态文件，且没有有意义的信息丢失。

**修复**：实现自动化整合周期。当 Agent 空闲时——任务之间或低优先级窗口期间——触发一个后台作业，读取原始日志，去重条目，根据最新数据解决矛盾，并写入一个干净的、压缩的状态文件。这保持 Agent 为下一次运行快速、廉价和准确。把它想象成对 AI 工作记忆进行碎片整理。

## 从哪里开始：最小可行 Harness

如果七层堆栈让你感到不知所措，不要在第一天就尝试构建所有内容。从第 7 层——约束与恢复——开始，然后逆向工作。你可以容忍不完美的 prompt。你可以容忍天真的工具集成。但你无法容忍一个在失败时破坏自己状态或静默吞咽错误的 Agent。

以下是第 1 天 harness 在实践中的样子：

- **state.json** —— 一个跟踪任务状态的单一结构化文件。如果进程死了，你可以从中断的地方继续。
- **重试包装器** —— 每个工具调用都有一个 try/catch，至少一次自动重试和指数退避。
- **Schema 验证器** —— 每个 LLM 输出在被接受之前根据 JSON schema 进行验证。格式错误的输出触发重试，而不是崩溃。
- **工具输出截断** —— 对每个工具载荷设置硬性 token 预算上限。上下文窗口内的静默截断是幻觉最常见的原因之一。

这四个组件可以在一个下午内构建。一旦你的 Agent 能够优雅地失败，你就赢得了让它变得更智能的权利。

## 结论

软件的未来是 Agent-first。随着模型获得自主生成和验证复杂系统的原始能力，人类价值发生转变。不再是关于写语法。而是关于设计使自主执行可靠的约束。

下一个十年最成功的构建者不是写出最好代码的人。而是构建最好 harness 的人——为最快的马建造最坚固的缰绳，而这些缰绳只不过是对一些原则的一致应用：约束、外化、验证和恢复。
